# 项目任务书：把学习变成面试证据

以下均为待实现项目，当前无代码和 benchmark。默认完成 **P-B 主项目 + P-A 一个小算子**；训练岗位改选 P-C。不要同时展开三个大工程。建项目目录时保留本任务书 ID。

## P-A · 一个算子的正确性与优化

建议目录：`Projects/OperatorLab/`。先选 softmax 或 Reduce，再决定是否深入 GEMM。目标：证明自己能定位瓶颈、提出改进并验证，而非要求必然超过成熟库。

| 里程碑 | 产物 | 验收 |
|---|---|---|
| A1 参考与输入 | CPU/框架参考、固定随机数据和边界样例 | 输入契约、容限、异常/尾块明确 |
| A2 基线 kernel | 可独立运行的实现、正确性检查 | 至少三种 shape，与参考比较 |
| A3 单次优化 | tiled/融合/访存改进之一 | 相同设备/输入/精度，原始重复计时 |
| A4 瓶颈与报告 | 时间线或 profiler 证据、一页总结 | 能解释为何有效或无效以及局限 |

硬件：CPU 可做 A1 和推导；A2–A4 的 GPU 结论必须实机验证。至少记录均值或中位数、波动、预热次数、测量次数、误差和实际设备型号。

面试故事：最初假设 → 正确性 bug → profiler 证据 → 修改 → 结果 → 哪些 shape 不受益。

## P-B · 推理服务基线与调度优化（默认主项目）

建议目录：`Projects/ServingLab/`。选 vLLM 或 SGLang 一个固定版本；模型选择以许可证、设备显存和运行兼容性为准，不预设必须运行某参数规模。

| 里程碑 | 产物 | 验收 |
|---|---|---|
| B1 约束 | 模型 revision、设备、质量要求、SLO 和容量估算 | 明确输入/输出长度分布、请求到达模型 |
| B2 基线 | 启动命令、配置、正确性用例、原始压测结果 | 冷启动和稳态分开；统计失败和超时 |
| B3 调度优化 | 调整一个支持的 batching/token budget 参数 | 固定负载，报告 TTFT/ITL/吞吐/显存 |
| B4 第二实验 | prefix cache 或 chunked prefill 的对照 | 明确冷/热缓存及混杂因素，质量不劣化 |
| B5 源码与可靠性 | 固定 commit 的调度/KV 路径，取消/过载演练 | 解释资源释放、排队和故障观测 |
| B6 项目答辩 | 一页报告、结果表、个人贡献与失败尝试 | 别人按文档复现，能接受两层追问 |

推荐负载矩阵：短输入/短输出、长输入/短输出、短输入/长输出、混合长度；每种至少三档负载，长度和负载值按设备实测填写。固定服务端生成参数并保存实际输出长度。报告 p50/p95/p99、样本量、错误率；样本不足以稳定估计尾部分位数时明确注明。

没有可用设备：先做 `Projects/SchedulerSim/` 的离散事件模拟，定义到达时间、输入长度、输出长度和每步成本模型，比较两种调度。保存事件轨迹并检查无请求丢失、取消后无资源残留。**它只能证明调度模型与代码，不能替代 B2–B4 的真实服务性能证据。**

## P-C · 小型分布式训练与扩展分析（训练方向）

建议目录：`Projects/DistributedLab/`。小模型、合成或可公开数据开始，不以模型规模作为成果。

| 里程碑 | 产物 | 验收 |
|---|---|---|
| C1 单进程 | 正确训练与恢复基线 | 参数/梯度/loss 检查 |
| C2 DDP | 两进程脚本、sampler/seed/global batch 说明 | 对齐单进程语义、无重复统计 |
| C3 显存方案 | DDP 与选定分片/重计算方案对比 | 固定模型/工作量，记录峰值与代价 |
| C4 扩展报告 | 通信/计算时间线、吞吐、效率 | 写明强扩展或弱扩展、实际 GPU 拓扑 |

CPU/Gloo 可以支持 C1–C2 的部分语义验证；NCCL、GPU 峰值与扩展效率需要实际多 GPU 运行。使用版本匹配的框架接口，脚本附一条完整运行命令。

## 统一交付标准

每个项目必须有独立 README 和依赖/版本说明；每次实验使用 [Experiment 模板](../Templates/Experiment.md)。保存小型原始 CSV/JSON、配置和命令；大权重/trace 不入库。Agent 提供的参考和用户独立实现部分要区分，完成里程碑不自动勾选所有相关知识项。
