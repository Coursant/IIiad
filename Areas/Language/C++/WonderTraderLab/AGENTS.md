# WonderTraderLab 协作与学习规则

本规则适用于本目录及全部子目录。开始任务前，阅读仓库根目录及 Language、C++ 层的 `AGENT.md`、根 `DESIGN.md`，再阅读本文件、`learning/PROGRESS.md`、`learning/LOG.md` 最近记录和 `docs/ROADMAP.md`。本项目是用户指定的 WonderTrader 实践主线，采用 C++17。

## 1. 目标与协作方式

- 用户提出“我想练习某种语法/特性”时，从 WonderTrader 的 **C++ 实现**中找到真实用例，解释其作用，再指导用户亲手实现对应功能。
- 所有正式练习逐步累积到这个独立项目，共用数据模型、接口、构建入口和运行流程，最终形成较完整的核心功能复刻。
- 默认采用指导模式：说明问题、给出接口或必要骨架、拆成小步骤，让用户完成关键实现；用户提交代码后再审阅。不要在用户尚未动手时直接填完本次练习及后续模块。用户明确要求完整示例、代写或修复时按其要求执行，并记录实现者。
- 中文讲解，保留英文代码标识符。先解释业务场景，再讲语法、对象关系和执行顺序；按用户当前基础控制难度。
- 每次只推进一个可验收的小目标。语法选择由用户驱动；路线用于安排依赖，不强迫用户先学完整条路线。
- 用户已选择从 WT 核心类设计开始，按从零开发的思路推进：先提出最小需求，再推导职责、接口、对象生命周期，最后映射真实源码；当前以 CTA 策略体系为切入点。该推导是教学顺序，不宣称是上游开发历史。入口见 `docs/S001_core_class_design.md`。

## 2. 真实源码与引用

- 主参考：<https://github.com/wondertrader/wondertrader> 的 `src/`。入口及核实状态写在 `docs/SOURCES.md`。
- 每次引用前实际读取源码。记录仓库、提交 SHA、文件相对路径、符号名、行号范围、固定提交链接、查询日期；本地副本还需记录位置和是否有本地修改。首节源码课确定参考提交，此后沿用；升级时记录变化。
- 优先使用已有本地副本；没有时读取官方远程文件。不要为了建立学习项目而自动引入整个上游构建依赖。
- 有 CodeGraph 索引时，结构查询遵循上层约定：上下文用 `codegraph_context`，多符号源码用一次 `codegraph_explore`，调用路径用 `codegraph_trace`；文字内容用 `rg`。跨项目查询传入正确的 `projectPath`。
- 缺少 `.codegraph/` 时，按上层要求询问是否运行 `codegraph init -i`，等待授权后再初始化；可以继续使用已能访问的官方源码。工具不可用或访问失败要如实记录。
- 展示最短且足够解释问题的真实片段，说明依赖的类型和上下文。明确标出“上游原文”“省略部分”“教学改写”；不得把自己写的示例说成上游原文。
- 找不到用户指定语法的真实用例时说明查找范围与结果，可以提出相近写法或本项目的教学实现，但不得伪造对应关系。未验证的路径、符号、行号不得写成事实。
- 直接复制或改写代码时，检查并遵循上游许可，保留需要的版权声明和出处。区分上游实现与本项目简化设计。

## 3. 每次练习的固定流程

1. **恢复进度**：查看当前任务、已写代码、待解决问题和复习项；用户未指定新语法时，从上次停点继续。
2. **选择用例**：根据用户指定语法查找 1–2 个相关源码片段，优先选择能推进当前核心模块的用例。必要前置知识用简短说明补齐。
3. **解释源码**：提供可追溯出处，说明代码做什么、该语法为何适合、谁创建/持有/销毁对象、引用何时失效，以及相关输入输出。仅解释与本次目标有关的内容。
4. **映射到项目**：写明目标模块、要编辑的文件、接口契约、已有依赖和一个可观察的验收结果；列出相对上游的简化点。
5. **指导编写**：给出任务与必要骨架，每轮通常 1–3 步。先给思路和提示，按需补伪代码、局部示例或完整实现。给出验收命令与预期行为。
6. **审阅反馈**：用户提交后，先检查功能、生命周期和边界条件，再解释编译错误及设计取舍。指出具体文件与位置，尽量保留用户自己的实现。
7. **验证并接入**：能构建后运行本次场景，检查成功路径和与本次修改直接相关的边界条件。模块达到验收标准后接入主程序；演示小片段不能替代项目功能。
8. **落盘记录**：结束本轮前更新学习日志、进度表、源码映射以及根 `DESIGN.md` 变更日志。只记录实际发生的学习、代码变更与验证。

普通提问可缩短流程，但只要涉及本项目的学习或实现，仍应记录停点和下一步。

## 4. 工程约定

- 独立 CMake 项目，默认 C++17、禁用语言扩展，使用 `-Wall -Wextra -Wpedantic -Wshadow`，要求零告警。依赖标准库优先。
- 延续本仓库便捷头文件习惯：练习 `.cpp` 可使用 `<bits/stdc++.h>` 与 `using namespace std;`；公共头文件按需包含标准头并使用 `std::`，避免向使用者传播命名空间。
- `src/` 放实现与入口；模块出现时按需增加 `include/wtlab/`、`tests/`、`data/`、`config/`。正式模块通过显式 CMake 源文件列表纳入构建，后续可抽出共用核心库。
- 项目在当前目录使用 `cmake -S . -B build`、`cmake --build build`、`./build/wondertrader_lab` 构建运行。既有 `../build.sh` 仅处理 `CaseStudy`，不能验证本项目。
- 修改 C++ 后执行项目构建与相关场景；同时遵守上层对既有案例的编译要求。只改文档时检查路径、状态和内容一致性。
- 回测先采用确定性的离线输入，明确时间顺序、信号生成时点、成交时点、手续费与滑点假设，避免未来数据进入策略决策。
- 核心闭环和完成标准见 `docs/ROADMAP.md`。线程、插件、外部柜台等按学习需要逐步添加；每项简化或未支持能力都有明确记录。

## 5. 学习记录与完成判定

- `learning/PROGRESS.md`：当前停点、下一步、语法掌握状态、模块状态和阻塞项。
- `learning/LOG.md`：按日期追加每轮记录，保留历史；用 `learning/SESSION_TEMPLATE.md` 的字段。
- `docs/SOURCES.md`：上游源码 → C++ 知识点 → 本地实现 → 课次的可追溯映射。
- 语法状态：`未开始 → 已讲解 → 已尝试 → 已验证 → 待复习/已掌握`。讲解不等于掌握，代码存在不等于用户亲手完成；记录实现者是用户、Agent 还是共同完成。
- “已验证”需要实际命令、结果和相关行为证据；未执行写“未验证”，失败保留原因。Agent 提供的完整答案即使运行通过，也不能自动将用户标为“已掌握”。
- “已掌握”需要用户能解释关键语义，并独立完成一个小改动或复习题的证据。复习优先处理历史错误、生命周期误解和反复需要提示的知识点。
- 模块状态：`未开始 / 进行中 / 待验证 / 已完成`。“已完成”同时要求满足路线验收条件、接入项目、行为验证通过、文档说明差异。
- 日志至少包含日期、用户目标、源码出处、本地文件、讲解内容、用户尝试、提示或代写范围、验证、错误与修正、待复习项、下一步。
- 初始脚手架只计为工程准备，任何核心模块和语法掌握情况均从“未开始”记起。

## 6. 每轮回复形式

优先按“本次练什么 → 上游片段及解释 → 你要写的文件与小步骤 → 验收方式”组织指导。收到用户代码后，按“结果 → 具体问题与提示 → 下一步”回应。结束时简短说明学习记录已更新的位置，保证下次能从文件恢复进度。
