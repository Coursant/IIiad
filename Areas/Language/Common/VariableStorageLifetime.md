# 沿着一个变量的完整生命周期，比较 Rust、C++ 与 Python

本文按“变量 → 初始化 → 类型推导 → 存储、生命周期与作用域 → ref/ptr → 赋值、复制与移动 → 清理”的顺序展开。一直使用一个装有 `[3, 7]` 的容器 `a`：Rust 用 `Vec<i32>`，C++17 用 `vector<int>`，Python 3.9+ 用 `list[int]`。

你提出的“move / copy / ref 由类型定义与默认语义共同决定”可以进一步写成：**先看这行代码是在创建对象、给已有对象赋值、建立引用，还是重新绑定名字；再看语言规则、具体类型，以及右侧表达式允许哪些操作。** C++ 还要看表达式的值类别和重载选择；Rust 要看 `Copy`、借用与所有权；Python 的普通名字赋值不调用类的复制操作。

## 1. 变量刚出现时，究竟创建了什么？

先看三行作用相近的代码：

| Rust | C++17 | Python |
|---|---|---|
| `let mut a = vec![3, 7];` | `auto a = vector<int>{3, 7};` | `a = [3, 7]` |

它们都让我们能通过 `a` 使用这两个数字，但需要区分三个层次：**名字 `a`、容器本身、容器所管理的元素**。

Rust 的 `a` 绑定一个 `Vec<i32>` 值，这个值拥有一块保存整数的缓冲区。C++ 的 `a` 是一个 `vector<int>` 对象，同样负责管理元素缓冲区。Python 的 `a` 是一个名字，绑定到列表对象；列表再持有元素对象的引用。

```text
Rust / C++ 的本例：
    局部容器 a ──拥有──> 元素缓冲区 [3, 7]

Python 的本例：
    名字 a ──绑定──> 列表对象 ──持有引用──> 整数对象 3、整数对象 7
```

这是所有权关系图，不是精确内存布局图。`vector` 的内部字段布局不由这里的示意图规定；Rust `Vec` 可理解为指针、长度、容量三部分，但字段顺序不保证；Python 的对象布局取决于解释器。不要据此认定每个名字都对应固定大小的栈槽，或者每个整数出现一次就必定重新分配一个对象。[Rust `Vec` 的存储保证](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees)、[Python 对象模型](https://docs.python.org/3/reference/datamodel.html#objects-values-and-types)。

这三个层次解释了后面的多数差异：复制容器，可能复制元素；复制持有容器的句柄，可能只增加一个所有者；复制地址或建立别名，可能完全不负责目标的销毁。

## 2. 初始化和类型推导：`auto` 没有决定一切

### 从声明中确定类型

| 问题 | Rust | C++17 | Python |
|---|---|---|---|
| 显式写类型 | `let mut a: Vec<i32> = vec![3, 7];` | `vector<int> a{3, 7};` | `a: list[int] = [3, 7]` |
| 省略类型 | `let mut a = vec![3, 7];` | `auto a = vector<int>{3, 7};` | `a = [3, 7]` |
| 类型何时确定 | 编译期，结合初始化和使用位置推导 | 编译期，根据初始化表达式等规则推导 | 对象在运行时有类型；注解供工具等使用 |
| 同一变量能换类型吗 | 同一绑定不能；重新写 `let a = ...` 可以遮蔽旧绑定 | 同一变量不能；转换后赋值仍保持原类型 | 名字可改绑到不同类型的对象 |
| 允许修改怎样表示 | 本例用 `mut` 允许修改 `Vec` | 本例不加 `const` 即可修改 | 普通名字赋值没有 `mut`/`const` 开关；对象是否可变看类型 |

Rust 的类型推导不只看字面量。例如 `let mut a = Vec::new(); a.push(3_i64);` 可以根据后面的使用推导出 `Vec<i64>`。但一旦这个绑定的类型确定，就不能再向其中压入字符串。

C++ 的 `auto` 是**编译期类型占位符**。`auto a = vector<int>{3, 7};` 最终仍然声明一个具体的 `vector<int>` 对象；它不会因为写了 `auto` 就自动变成引用，也不会让后续赋值变成动态类型操作。[C++17 `auto` 推导规则](https://timsong-cpp.github.io/cppwp/n4659/dcl.spec.auto)。

初始化表达式的形式也有影响：`auto a = {3, 7};` 推导为 `initializer_list<int>`，不会自动得到可追加元素的 `vector<int>`。本文明确写出 `vector<int>{3, 7}`，让 `auto` 推导的目标类型清楚可见。

Python 的 `a: list[int]` 不会让解释器自动禁止 `a = "hello"`，也不会自动检查列表的每个元素。静态检查器可以报告与注解不一致的代码；Python 运行时通常不替你执行这种类型检查。[Python 类型注解](https://docs.python.org/3/library/typing.html)。

### 同样写 `auto`，是否复制取决于声明方式

以下各行都假设 C++ 中已经有 `vector<int> a{3, 7};`，并分别考察：

| 写法 | 推导后的类型 | 这行实际建立什么 |
|---|---|---|
| `auto b = a;` | `vector<int>` | 一个新容器，复制 `a` 的元素 |
| `auto& r = a;` | `vector<int>&` | 引用原来的容器，不复制容器 |
| `const auto& r = a;` | `const vector<int>&` | 通过此引用只读原容器 |
| `auto* p = &a;` | `vector<int>*` | 一个保存容器地址的指针对象 |
| `auto b = move(a);` | `vector<int>` | 用右值表达式初始化新容器，选择移动构造 |
| `auto&& r = a;` | `vector<int>&` | 此处发生引用折叠，仍是引用原容器 |

还有一个容易误判的情况：`const vector<int>& r = a; auto b = r;` 中，`b` 是独立的、非 `const` 的 `vector<int>`；普通按值 `auto` 推导不会保留这里的引用和顶层 `const`。若要保留引用，明确写 `auto&` 或 `const auto&`。

Rust 的对应写法是 `let r = &a;` 和 `let r = &mut a;`：`&` 出现在表达式中，推导后的类型分别是 `&Vec<i32>`、`&mut Vec<i32>`。`let b = a;` 的类型仍是 `Vec<i32>`，它会移动所有权，不会自动解释成借用。

Python 的 `b = a` 让两个名字绑定同一对象。这里没有与 C++ `auto&` 完全相同的声明语法，也没有 Rust 的借用检查。

### 声明不一定已经产生了可读的值

| 写法 | 含义 |
|---|---|
| C++ 函数内的 `int n;` | `n` 未初始化；不能把它当成可安全读取的整数 |
| C++ 的 `int n{};` | 初始化为 `0` |
| C++ 的 `vector<int> a;` | 调用默认构造，得到有效的空容器 |
| Rust 的 `let n: i32;` | 可以先声明，但编译器要求在读取前完成初始化 |
| Python 函数内的 `n: int` | 仅有注解，不会为名字绑定整数对象；此时读取会失败 |

所以不能用一条“所有局部变量默认是 0”或“没有赋值就没有对象”的规则跨语言解释。初始化行为由语言和类型共同决定。

## 3. 存储、生命周期、作用域：三个不同的问题

**存储**问的是值和资源放在哪里；**生命周期**问的是某个对象从何时开始有效、何时结束；**作用域**问的是源码的哪些位置能用某个名字找到它们。它们经常一起变化，但并不相同。

在函数中创建的局部容器通常可以画成“局部容器控制信息 → 动态元素缓冲区”。函数返回时，局部变量的作用域结束；只要通过合法返回、移动或其他持有方式把资源交给外部，缓冲区就可以继续存在。反过来，名字还在作用域里，也不代表它一定可读：Rust 的变量可能已被移动，C++ 指针可能已经悬空。

### C++：对象有存储期，资源由类型管理

C++ 区分自动、静态、线程和动态存储期。它们描述存储持续多久，并不只是“栈或堆”的另一种叫法。[C++17 存储期分类](https://timsong-cpp.github.io/cppwp/n4659/basic.stc)。

| 例子 | 要区分的对象和生命周期 |
|---|---|
| 函数内 `vector<int> a{3, 7};` | `a` 有自动存储期；正常离开作用域时析构，释放所拥有的元素资源 |
| 函数内 `static vector<int> a{3, 7};` | 名字只在局部可见，对象可跨多次函数调用存在 |
| `thread_local vector<int> a;` | 每个线程有相应对象，按线程存储期管理 |
| 函数内 `auto p = new vector<int>{3, 7};` | `p` 是自动存储期的裸指针；`new` 创建的容器具有动态存储期，离开 `p` 的作用域不会自动销毁它 |
| `auto owner = make_unique<vector<int>>(2, 7);` | 局部智能指针管理动态创建的容器；智能指针销毁时自动清理目标，除非此前已转移或释放拥有权 |

普通局部 `int`、`vector` 对象经常放在栈上，也可能被优化进寄存器或消除；不能把具体机器布局当成语言语义。也不能看到 `vector` 的元素在动态存储区，就说局部 `vector` 对象本身也必定在堆上。

#### 从 `new` 开始拆开看：指针变量、动态对象、元素缓冲区

执行 `auto p = new vector<int>{3, 7};` 时，普通 `new` 表达式为容器取得存储，并在该存储中初始化一个 `vector<int>`，最后产生指向它的指针。这个指针值用来初始化局部变量 `p`，所以 `auto` 推导出的是 `vector<int>*`。[C++17 `new` 表达式](https://timsong-cpp.github.io/cppwp/n4659/expr.new)。

这行代码中有三个要分别追踪的东西：

```text
局部指针变量 p
    │ 保存地址；p 自身有自动存储期
    ▼
new 创建的 vector<int> 对象
    │ 有动态存储期；管理自己的元素存储
    ▼
元素缓冲区 [3, 7]
```

容器对象和元素缓冲区是两层分别管理的存储。与 `vector<int> a{3, 7};` 相比，变化在于容器对象本身也被动态创建了。`new` 并没有把指针变量 `p` 自身变成动态存储期的对象。

动态创建的容器通常没有单独的变量名；`p` 只是访问它的一条路径。下面的完整程序让这个区别变得可见：

<!-- example: cpp-new-lifetime -->
```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    vector<int>* saved = nullptr;
    {
        auto p = new vector<int>{3, 7};
        auto& r = *p;
        r[0] = 4;
        saved = p;       // 复制地址，容器没有被复制
    }                    // p 和 r 的作用域结束；动态容器仍存在

    assert(saved->size() == 2 && (*saved)[0] == 4);
    delete saved;        // 销毁容器，并释放其对象存储
    saved = nullptr;     // 另行修改指针变量，避免保留失效地址
}
```

`p` 离开作用域时不会自动执行 `delete p`。程序通过 `saved` 保留地址，因而仍可使用对象；即使没有保留地址，动态对象也不会因此自动清理。若丢失了最后一条能用于释放它的访问路径，就会造成内存泄漏。

这里执行 `delete saved` 时，先调用 `vector` 的析构函数，由它销毁元素、释放元素缓冲区，再释放动态 `vector` 对象本身的存储。`saved` 这个局部指针变量仍然存在，`delete` 不会替你把它改成空指针。[C++17 `delete` 表达式](https://timsong-cpp.github.io/cppwp/n4659/expr.delete)。

如果还有另一个指针 `q` 保存同一地址，删除目标后，`q` 也不能继续用于访问目标。随后把 `saved` 设成 `nullptr` 只改变 `saved`，不会更新 `q`。指针的作用域、目标的生命周期与其他别名的有效性，由此分成了三件事。

#### `new` 后怎样初始化，决定创建的是哪种对象

| 表达式 | 创建的对象及初始状态 | 对应释放方式 |
|---|---|---|
| `new int` | 一个默认初始化的 `int`；在 C++17 中值不确定，不能直接读取 | `delete p` |
| `new int{}` | 一个初始化为 `0` 的 `int` | `delete p` |
| `new int{7}` | 一个初始化为 `7` 的 `int` | `delete p` |
| `new int[3]{}` | 三个均为 `0` 的整数，返回首元素指针 | `delete[] p` |
| `new vector<int>{3, 7}` | 一个包含两个元素的容器对象 | `delete p` |

`new vector<int>{3, 7}` 创建的是**一个容器对象**，因此使用 `delete`；容器内部有多个元素，并不意味着应该对容器指针使用 `delete[]`。`new[]` 与 `delete[]`、普通 `new` 与 `delete` 的配对取决于对象是如何创建的。

还要区分 `new T(...)` 这个表达式与 `operator new` 分配函数：前者包含对象初始化，后者主要提供原始存储。`malloc`/`free` 不会替 C++ 类执行构造/析构，也不能与本例的 `new`/`delete` 随意混用。进一步的 placement new 可以在已有存储上构造对象，说明“取得存储”与“开始对象生命周期”本来就是不同步骤。

#### 用智能指针把动态对象的清理责任交给局部拥有者

在理解手动 `new`/`delete` 后，可以把清理责任写进类型：

<!-- example: cpp-new-owner -->
```cpp
// 片段：放在函数内
auto owner = make_unique<vector<int>>(initializer_list<int>{3, 7});
auto* p = owner.get();
auto& r = *owner;
r[0] = 4;
assert(p->at(0) == 4);
owner.reset();           // 此刻清理动态容器及其元素资源
// 此后不再通过 p 或 r 访问目标；它们不会因为 owner.reset() 自动变安全。
```

`owner` 的类型是 `unique_ptr<vector<int>>`，负责目标的销毁；`p`、`r` 只负责访问。若没有提前 `reset()` 或移交拥有权，正常离开作用域以及异常展开都会触发拥有者清理。与手动 `new` 相比，动态对象仍然存在，只是“谁调用删除操作”被写进了类型。

### Rust：所有者负责值，借用有自己的有效区间

本例 `a: Vec<i32>` 拥有元素缓冲区；正常离开拥有它的作用域时执行清理。如果 `a` 的值已移给 `b`，清理责任转交给 `b`；原位置不能再读取旧值。

Rust 的 `&T` 或 `&mut T` 还有**借用生命周期**。它表示该引用允许被使用的区间，不是“额外设置一个计时器来延长目标寿命”。编译器必须证明这个区间内目标有效。[Rust 引用与借用](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)。

借用在最后一次使用后可能结束，而 `Vec` 本身仍然活着。不要把“借用结束”理解成“目标被 Drop”。局部所有者的正常清理、提前 `drop(a)`、覆盖已有值时的清理，才是这里需要分别追踪的事件。[Rust 析构与 drop scope](https://doc.rust-lang.org/reference/destructors.html)。

Rust 的 `static` 值具有整个程序执行期间的存储期，而且不会在程序结束时自动调用 `Drop`；`const` 定义可在使用点使用的常量值，不代表必须有一个唯一且稳定地址的对象。`Box<T>` 则显式拥有一个堆分配的 `T`。这些概念不能直接照搬 C++ 的存储期分类。[Rust `static`](https://doc.rust-lang.org/reference/items/static-items.html)、[`const`](https://doc.rust-lang.org/reference/items/constant-items.html)。

#### 对照 C++ 的动态对象：`Box::new`

Rust 没有对应的 `new` 语言关键字。`Box::new` 是标准库关联函数，创建一个拥有堆上值的 `Box<T>`。因此 `Box::new(vec![3, 7])` 的结果是 `Box<Vec<i32>>`，其作用更接近拥有动态容器的 `unique_ptr`，而不是一个需要手动 `delete` 的裸指针。[Rust `Box`](https://doc.rust-lang.org/std/boxed/index.html)。

<!-- example: rust-box-lifetime -->
```rust
fn main() {
    let mut owner = {
        let p = Box::new(vec![3, 7]);
        p                       // 把 Box 所有权移出这个块
    };

    let r = &mut *owner;         // 借用堆上的 Vec
    r[0] = 4;
    assert_eq!(r.as_slice(), &[4, 7]);
    drop(owner);                // 清理 Vec、元素缓冲区和 Box 的目标存储
    // 不能在这里继续使用 owner 或借用 r。
}
```

局部 `Box` 句柄、堆上的 `Vec` 对象、`Vec` 的元素缓冲区同样是三个层次。`p` 的名字结束时，值已经移给外层的 `owner`，所以清理责任也转交给外层。若没有移出块，`p` 的拥有值会在块结束时清理；若不显式 `drop(owner)`，则由 `owner` 的正常作用域结束触发清理。

移动 `Box` 句柄不会移动它所拥有的堆对象。另一个常用写法 `let a = vec![3, 7];` 已经会为元素分配缓冲区，**不需要为了让元素位于堆上而再包一层 `Box<Vec<_>>`**。额外使用 `Box` 的区别是把 `Vec` 对象本身也放到堆上。

### Python：名字结束与对象回收分开考虑

函数中的 `a` 是局部名字。函数返回后，局部绑定通常随调用结束而释放；但如果返回了这个对象，或其他容器、闭包等还保留它，对象就仍可达。

Python 的 `if`、`for` 不建立类似 C++ `{ ... }` 的普通局部块作用域。例如 `if True: a = [3, 7]` 执行后，`a` 仍可在所在函数的后续代码中使用。函数、类、模块等各有自己的名字规则。[Python 执行模型](https://docs.python.org/3/reference/executionmodel.html)。

当列表不再可达时，它可以被回收。CPython 通常使用引用计数并辅以循环垃圾回收；Python 语言本身不保证“最后一个名字消失的瞬间就析构”。即使对象已释放，其内存也可能由运行时分配器保留以便复用，不能用进程内存是否立刻下降判断对象是否仍活着。

#### 对照 `new`/`delete`：对象由解释器管理，`del` 操作绑定

Python 写 `p = [3, 7]` 就创建列表并绑定名字，不需要显式 `new`。在 CPython 中，对象及列表的元素引用存储由运行时分配器管理；Python 源码没有对应“这个列表是自动存储期还是由 `new` 创建”的选择。

<!-- example: python-object-lifetime -->
```python
def make_numbers():
    p = [3, 7]
    r = p
    del p                      # 删除名字 p；r 仍保留同一列表
    r[0] = 4
    return r


a = make_numbers()             # 局部名字结束，返回的列表仍有效
assert a == [4, 7]
del a                         # 本例列表此后不可达，可被回收
```

`del a` 与 C++ `delete p` 不同：前者删除名字绑定，后者销毁所指对象并释放存储。Python 中如果另一个名字仍持有同一对象，`del a` 不会使它悬空。

普通 Python 类调用通常通过 `__new__` 创建实例，再由 `__init__` 初始化；这两个步骤也区分创建与初始化，但 `__new__` 是 Python 对象协议中的特殊方法，不是 C++ 的 `new` 表达式。列表字面量的创建也无需手动调用这些方法。[Python 对象创建协议](https://docs.python.org/3/reference/datamodel.html#object.__new__)。

| 创建与清理的步骤 | C++ 裸 `new` | Rust `Box::new` | Python 列表 |
|---|---|---|---|
| 得到什么 | 指向动态对象的 `T*` | 拥有堆上值的 `Box<T>` | 名字绑定到列表对象 |
| 局部名字结束时 | 指针消失，目标不会因此自动删除 | 若值未移走，则清理目标 | 释放绑定；是否回收还看其他持有关系 |
| 交给外层怎样表达 | 可以复制地址，但清理责任须由程序约定 | 移动 `Box`，同时转交所有权 | 返回或赋值，让外层名字继续持有对象 |
| 主动提前清理 | `delete p`，其他别名随即不能访问目标 | `drop(owner)`；安全借用必须允许此次操作 | `del name` 只删除该绑定，不强制销毁仍可达对象 |

从这一层继续看下一节的 ref/ptr，就要问清楚：建立的是访问路径，还是把动态对象的清理责任也交给了这个变量。

## 4. 为 `a` 创建 ref/ptr：获得访问路径，还是承担清理责任？

对本例而言，**借用引用、裸指针、拥有资源的智能指针**需要分开理解。它们都能帮助访问对象，但并不是每一种都负责让目标继续活着。

### C++：引用绑定对象，指针保存地址

```cpp
// 片段：放在函数内
vector<int> a{3, 7};
auto& r = a;
auto* p = &a;
r[0] = 4;
p->push_back(10);
// a 现在为 [4, 7, 10]
```

`r` 引用的就是 `a` 这个 `vector` 对象；`p` 则是另一个对象，它保存 `a` 的地址。通过它们修改的都是同一个容器。这里既没有复制容器，也没有增加一个能延长 `a` 寿命的所有者。

引用初始化后不能改绑：`r = other;` 会给 `a` 赋值。指针可以改指向：`p = &other;` 修改的是指针保存的地址。`*p = other;` 才是给 `p` 当前指向的容器赋值。[C++17 引用初始化与赋值](https://timsong-cpp.github.io/cppwp/n4659/dcl.init.ref)。

`const vector<int>* p` 限制通过 `p` 修改目标；`vector<int>* const p` 限制修改指针自身。前者还可以指向别处，后者仍可以修改所指的非 `const` 容器。`const` 不会自动变成共享所有权，也不保证没有其他别名能够修改对象。

本例中，`a` 析构后再通过 `r` 或 `p` 访问就会产生悬空访问。另有“某些局部引用绑定临时对象时延长临时对象寿命”的规则，但不能把它推广成“给已有局部对象建立引用就可以延寿”。

### Rust：引用是受检查的借用

```rust
// 片段：放在函数内
let mut a = vec![3, 7];
let r = &a;
assert_eq!(r[0], 3);     // r 的最后一次使用
let w = &mut a;
w[0] = 4;
w.push(10);             // w 的最后一次使用
assert_eq!(a, vec![4, 7, 10]);
```

`r` 的类型是 `&Vec<i32>`，它允许共享读取；`w` 的类型是 `&mut Vec<i32>`，它允许独占修改。对于本例这种普通 `Vec<i32>`，共享借用仍需要继续使用时，不能同时创建冲突的可变借用。

`let w = &mut a` 不需要写 `let mut w` 就可以修改 `a`：`&mut` 说明能通过这个引用修改目标；`let mut w` 则说明变量 `w` 自身可以重新赋值。这是两个不同层面的可变性。

Rust 的引用本身可以是可重新赋值的变量。例如 `let mut r = &a; r = &b;` 是让引用值改指向 `b`；若 `w: &mut Vec<i32>`，`*w = vec![1];` 是替换被借用位置里的容器值。它与 C++ 引用不可改绑的规则不同。

也可以创建裸指针：`let p: *const Vec<i32> = &a;`。裸指针不承担所有权，解引用需要 `unsafe`，程序员必须保证目标有效。`unsafe` 只允许表达某些操作，并不自动使悬空访问正确。[Rust 指针与解引用](https://doc.rust-lang.org/reference/expressions/operator-expr.html#the-dereference-operator)。

### Python：另一个名字绑定同一个对象

```python
# 片段
a = [3, 7]
r = a
r[0] = 4
r.append(10)
assert a == [4, 7, 10]
```

这里的 `r` 是同一列表对象的另一个名字绑定。与 C++ 裸引用、Rust 借用相比，一个实际差异是：只要 `r` 仍能到达该对象，即使执行 `del a`，列表也仍可通过 `r` 使用。

不过 `r` 不是对“变量 `a` 的绑定槽位”的引用。以后执行 `a = [1]`，只会改变 `a` 的绑定；`r` 仍绑定旧列表。Python 普通代码没有“取局部变量槽位地址再修改该槽位”的 C++ 式 `&a` 操作。`id(a)` 也不是可用来解引用的语言级裸指针。

### 真正需要管理寿命时，选什么类型？

| 意图 | Rust | C++17 | Python |
|---|---|---|---|
| 临时读取已有对象 | `&T` | `const T&`、`const T*` | 普通对象引用，但没有同等借用限制 |
| 临时修改已有对象 | `&mut T` | `T&`、`T*` | 对可变对象进行方法调用或元素赋值 |
| 独占拥有动态对象 | `Box<T>` | `unique_ptr<T>` | 普通引用无静态独占所有权保证 |
| 多方共同持有对象 | `Rc<T>`；需要线程安全计数时用 `Arc<T>` | `shared_ptr<T>` | 普通强引用可共同保留对象 |
| 观察但不保活 | `Weak<T>` | `weak_ptr<T>` | 支持弱引用的对象可用 `weakref.ref` |

这张表对应的是意图，不意味着类型可以直接替换。`Rc<T>`/`Arc<T>` 不会让普通 `T` 自动支持任意共享修改；引用计数也不是线程间数据同步。Python 内置 `list` 不能直接用 `weakref.ref`，需要支持弱引用的包装对象等方式。[Rust `Rc`](https://doc.rust-lang.org/std/rc/struct.Rc.html)、[Python 弱引用](https://docs.python.org/3/library/weakref.html)。

创建智能指针时还要观察是否创建了新目标：`make_unique<vector<int>>(a)` 会创建新的 `vector` 并复制 `a`；`Box::new(a)` 会把 `a` 的值移入 `Box`。不要用 `unique_ptr` 或 `shared_ptr` 接管普通局部对象的地址，它们的默认释放方式不适用于这种对象。

## 5. 轮到 `=`：先判断它出现在哪一种语境

现在已经有容器 `a`，希望再引入 `b`。下面三行都很短，结果却不同：

| Rust | C++17 | Python |
|---|---|---|
| `let b = a;` | `auto b = a;` | `b = a` |
| 移动 `Vec`；原 `a` 的值不可再读 | 复制 `vector`；`a`、`b` 各自有容器和元素缓冲区 | 增加名字绑定；`a`、`b` 指向同一个列表 |

这不是由 `=` 这个字符单独决定的。还需要看左边是在声明新变量还是操作已有变量，以及值的类型是什么。

### C++：初始化、赋值、引用绑定分别处理

假设每一行分别在已有 `vector<int> a{3, 7};` 的环境中考察：

| 代码 | 操作 | 对 `a` 的影响 |
|---|---|---|
| `auto b = a;` | 复制构造一个新 `vector` | `a` 不变 |
| `auto b = move(a);` | 移动构造一个新 `vector` | `a` 仍是活着的对象，处于有效但状态未指定的可移动后状态 |
| `b = a;`，`b` 已存在 | 调用复制赋值操作 | 用 `a` 的内容更新 `b`，`a` 不变 |
| `b = move(a);`，`b` 已存在 | 调用移动赋值操作 | 更新 `b`，同时把 `a` 置于相应移动后状态 |
| `auto& b = a;` | 绑定引用 | 不复制也不转移容器 |
| `auto* p = &a;` | 初始化指针 | 保存地址，不接管容器 |

`auto b = a` 虽然写了等号，但它是**初始化**，会涉及构造函数；已经有 `b` 以后写 `b = a` 才是**赋值**，会涉及 `operator=`。C++ 类可以分别定义这些操作，二者不能混为一谈。[C++17 复制与移动操作](https://timsong-cpp.github.io/cppwp/n4659/class.copy)。

`move(a)` 自身只是把表达式转换为适合参与移动重载选择的形式，并没有执行资源转移。实际行为由后续选中的构造函数或赋值运算符完成。若类型没有可用的移动操作，可能改用接受 `const T&` 的复制操作；若选中了被删除的操作，则编译失败。`const` 对象一般也不能交给常见的 `T(T&&)` 移动构造函数。[C++17 `std::move`](https://timsong-cpp.github.io/cppwp/n4659/forward)。

因此，`auto&& r = move(a);` 只是建立一个右值引用，并没有凭空构造第二个容器。`r` 这个有名字的表达式本身又是左值；`auto b = r;` 对本例仍然复制，想参与移动选择需要再次明确使用 `move(r)`。

对本例的 `vector<int>`，移动之后可以给 `a` 重新赋值、调用无前置条件的操作或让它析构；不能直接假定它仍有原来的元素，也不要把“移动后必为空”当作一般规则。自定义类移动后的状态由自己的操作约定决定，不自动获得所有标准库类型的保证。[C++17 标准库对象的移动后状态](https://timsong-cpp.github.io/cppwp/n4659/lib.types.movedfrom)。

已有容器的赋值也不等于“先销毁整个 `b` 对象，再创建一个同名对象”。`vector` 可以在赋值期间复用自己的存储；`b` 仍是原来那个容器对象，其内部资源可以变化。

如果被复制的变量本身是指针，效果又不同。`auto p = &a; auto q = p;` 复制的是地址值：`p`、`q` 是两个独立的指针对象，但指向同一个容器。随后 `q = nullptr;` 只改变 `q`；通过仍然有效的 `p` 修改目标仍会影响 `a`。因此“复制了变量的值”与“复制了它所指向的对象”必须分开说。

### Rust：按值使用时，根据 `Copy` 决定复制或移动

| 右侧 `a` 的类型 | `let b = a;` 的一般结果 | 之后能否读取原 `a` |
|---|---|---|
| `i32`、`bool` 等 `Copy` 类型 | 隐式复制值 | 可以 |
| `Vec<i32>`、`String` | 移动值及所有权 | 重新初始化前不可以 |
| `&T` | 复制共享引用值，不复制目标 `T` | 可以继续使用两个共享引用 |
| `&mut T` | 在无预期类型约束的普通 `let b = a` 中移动引用值 | 原引用不能继续使用；调用等语境可能自动重借用 |
| `Box<T>`、`Rc<T>`、`Arc<T>` | 移动该拥有者句柄 | 原绑定不能继续使用；不会隐式增加引用计数 |

`Copy` 是类型的能力声明，允许按值使用时隐式复制；`Clone` 是显式调用的复制接口。`let b = a` 不会因为某个类实现了 `Clone`，就自动替你调用 `a.clone()`。[Rust `Copy`](https://doc.rust-lang.org/std/marker/trait.Copy.html)、[`Clone`](https://doc.rust-lang.org/std/clone/trait.Clone.html)。

对于 `Vec<i32>`，`let b = a.clone();` 会建立独立容器并复制整数元素。对于 `Rc<Vec<i32>>`，`Rc::clone(&a)` 创建另一个指向同一分配的拥有者句柄。两者都叫 clone，但复制到哪一层取决于具体类型。

Rust 的普通 `=` 不能像 C++ 的 `operator=` 那样由自定义类型重载。对本例的 `b = a`，先求得右侧的值，再清理 `b` 原有的已初始化值，然后把新值写入 `b`；右侧是 `Vec` 时发生移动。`Drop` 可以定义旧值的清理行为，但它不是自定义赋值运算符。[Rust 赋值表达式](https://doc.rust-lang.org/reference/expressions/operator-expr.html#assignment-expressions)。

Rust 移动也不是可以定义一个 `move()` 钩子来拦截的操作。它转移值的可用位置与所有权；机器代码是否真正搬运字节由实现和优化决定。对于 `Vec`，不需要复制它管理的整批元素。

移动后的原位置可以重新初始化：`let mut a = vec![3, 7]; let b = a; a = vec![1];` 是合法的。这时 `a` 保存新值，`b` 拥有旧值；同一位置不会把已移走的旧资源再次释放。

### Python：名字赋值就是绑定；复制必须显式表达

| 写法 | 实际含义 |
|---|---|
| `b = a` | `b` 绑定 `a` 当前所指的对象 |
| `b = a.copy()`，`a` 是列表 | 新建外层列表，元素对象引用被复制 |
| `b = copy.copy(a)` | 请求浅复制，具体行为可由类型定制 |
| `b = copy.deepcopy(a)` | 请求递归复制；共享关系、循环和自定义复制逻辑由协议处理 |
| `b = [1]`，`b` 已存在 | 将 `b` 改绑到新列表；旧对象是否继续存在看其他持有关系 |
| `b[0] = 1` | 修改 `b` 所指容器中的元素位置 |

对 `[3, 7]` 这样的整数列表，浅复制足以让“修改某个槽位”互不影响；但若 `a = [[3], [7]]`，`b = a.copy()` 后两个外层列表仍引用同样的内部列表。此时 `b[0].append(4)` 也能通过 `a` 观察到。[Python 复制协议](https://docs.python.org/3/library/copy.html)。

`b = a` 的普通名字绑定不能通过给类定义 `__copy__` 改成复制，也没有对应 C++ `operator=` 的普通名字赋值钩子。赋值的**目标形式**则很重要：`obj.field = value` 可能经过 `__setattr__` 或描述符，`obj[index] = value` 可以经过 `__setitem__`。这些是在操作对象，不是在改变普通局部名字赋值的规则。[Python 赋值语句](https://docs.python.org/3/reference/simple_stmts.html#assignment-statements)。

`+=` 还需要另外判断。对列表，`b += [10]` 通常原地修改同一列表，因此别名能够看到；`b = b + [10]` 新建列表并改绑 `b`，旧别名仍指向原列表。对整数这样的不可变对象，`b += 1` 则让名字绑定计算结果，不会原地修改整数对象。

### 若 `b` 已经有旧内容，旧内容去了哪里？

| 语言 | 执行前 `b` 已有值，再执行 `b = a` |
|---|---|
| C++ `vector<int>` | 原 `b` 对象继续存在；复制赋值更新其元素和存储，可能复用缓冲区 |
| Rust `Vec<i32>` | `b` 原有的 `Vec` 值被清理，随后接收从 `a` 移来的值 |
| Python `list` | `b` 改绑到 `a` 所指列表；原来那张列表若还有其他引用就继续存在 |

“变量名没变”不表示三个过程相同。尤其要看之前创建的 ref/ptr：它们可能引用容器对象，可能借用一个即将被替换的值，也可能独立持有旧列表。

## 6. 类型定义如何参与决定 copy / move / ref？

用“包含一个容器的类型”继续这个例子，就能看到类型设计对默认操作的影响。

### C++：成员类型与特殊成员函数共同决定

```cpp
// 类型定义片段
struct Values {
    vector<int> data;
};
struct SharedValues {
    shared_ptr<vector<int>> data;
};
struct UniqueValues {
    unique_ptr<vector<int>> data;
};
```

| 类型 | 从普通左值初始化 `auto b = a;` | `auto b = move(a);` |
|---|---|---|
| `Values` | 默认复制成员 `vector`，得到独立整数容器 | 默认移动成员 `vector` |
| `SharedValues` | 复制 `shared_ptr`，共同拥有同一个容器 | 移动 `shared_ptr` 句柄 |
| `UniqueValues` | 不允许复制；成员 `unique_ptr` 不可复制 | 可以移动独占所有权 |

默认复制是按成员的语义进行的，不是无条件的深复制。若成员换成裸指针 `vector<int>*`，默认复制只复制地址，既不复制目标，也不自动建立安全的共同所有权。如果这个类同时在析构时 `delete` 该地址，就需要正确设计复制与移动，否则会出现重复释放等问题。

即使显式请求编译器生成默认移动操作，裸指针成员也不会自动把源指针清成空；其地址值仍可能同时留在两个对象中。`unique_ptr` 的移动能正确移交清理责任，正是因为它这个类型实现了相应语义。

自定义类可以定义或删除 `T(const T&)`、`T(T&&)`、`operator=(const T&)`、`operator=(T&&)`，分别控制复制构造、移动构造、复制赋值、移动赋值。编译器是否生成某些默认操作还受其他特殊成员函数影响，例如自行声明析构函数会阻止自动生成移动操作。对上面这种只组合资源管理成员的类型，让成员自己管理资源通常更容易保持正确。

因此“默认 copy”的意思不是“编译器替所有类执行同一种复制算法”；它还要遵循成员类型提供的操作和语言的生成规则。

### Rust：`Copy` 要明确实现，`Clone` 要显式调用

```rust
// 类型定义片段
#[derive(Clone)]
struct Values {
    data: Vec<i32>,
}

#[derive(Clone, Copy)]
struct Number {
    value: i32,
}
```

`Values` 可以 `a.clone()`，但 `let b = a` 仍然移动。因为 `Vec<i32>` 不实现 `Copy`，也不能给 `Values` 合法地派生 `Copy`。

`Number` 则因为明确实现了 `Copy`，在 `let b = a` 时复制。仅仅因为一个结构体的字段都是整数，并不意味着该结构体自动实现了 `Copy`；类型定义需要选择这个能力。

`Copy` 的复制不能定制成“分配内存然后深复制”；自定义逻辑放在 `Clone::clone` 中。实现了 `Drop` 的类型不能同时实现 `Copy`，因为两份可独立清理的值可能破坏资源管理。`Clone` 也不承诺深复制：派生的 `Clone` 会调用各成员自己的克隆操作，成员若是 `Rc`，克隆的就是共享句柄。

### Python：类可以决定显式复制，不能改变普通名字绑定

```python
# 类型定义片段
class Values:
    def __init__(self, data):
        self.data = list(data)

    def __copy__(self):
        return Values(self.data)
```

这个类为 `copy.copy(a)` 定义了复制方式。它会创建新的 `Values` 和新的外层列表；对整数元素已经足够独立，对嵌套可变元素仍然只是浅复制。

但是 `b = a` 永远不会因此自动调用 `__copy__`。它仍然让 `a` 和 `b` 绑定同一个 `Values` 对象。类可以控制对象操作的行为；普通名字绑定的基本语义由语言固定。

这样就能准确修正最初的判断：**类型确实影响 copy/move 的能力与具体效果，但三种语言留给类型定制的入口不同。不能用“类自己决定等号的一切”统一解释。**

## 7. 把整个生命周期连起来：`a`、`r`、`b`、`c` 最后各自指向什么？

下面三段是可独立运行的完整程序。数据始终从 `[3, 7]` 开始，经别名或借用改成 `[4, 7, 10]`；再做一份独立副本 `b`，把原资源交给或共享给 `c`，最后让 `a` 得到 `[1]`。这里刻意保留语言之间的语义差异。

### C++17 完整程序

<!-- example: cpp-lifecycle -->
```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    // 1. a 是拥有元素缓冲区的 vector<int> 对象。
    auto a = vector<int>{3, 7};

    // 2. r 与 p 都指向 a 这个容器对象，不负责销毁它。
    auto& r = a;
    auto* p = &a;
    r[0] = 4;
    p->push_back(10);
    assert((a == vector<int>{4, 7, 10}));

    // 3. b 是独立副本。
    auto b = a;
    b[0] = 99;
    assert(a[0] == 4);

    // 4. 移动构造 c；a 这个容器对象仍然存在。
    auto c = move(a);
    assert((c == vector<int>{4, 7, 10}));

    // 5. 给仍然存在的 a 赋新值。
    a = vector<int>{1};
    assert(r[0] == 1);
    assert(p == &a && p->at(0) == 1);
    assert(c[0] == 4);
    assert(b[0] == 99);

    // 6. 正常离开作用域，c、b、a 各自清理所拥有的资源。
}
```

关键在第 4、5 步。`move(a)` 没有让 `a` 的名字改绑到另一个对象，也没有让 `r` 改为引用 `c`。`r` 和 `p` 一直指向原来那个容器对象 `a`；当 `a` 得到新内容 `[1]` 后，通过它们看到的也是 `[1]`。

这与指向**元素**的指针是两个问题。`&a` 指向容器对象，`&a[0]` 指向缓冲区中的元素。`push_back` 扩容可能使旧元素地址失效，而容器对象的地址仍保持不变。对本例这种普通 `vector` 移动构造，原有元素引用可以继续指向由新容器接管的元素；不能把“引用容器”和“引用元素”混成同一条规则。[C++17 容器移动与引用规则](https://timsong-cpp.github.io/cppwp/n4659/container.requirements.general)、[`vector` 修改操作](https://timsong-cpp.github.io/cppwp/n4659/vector.modifiers)。

### Rust 完整程序

<!-- example: rust-lifecycle -->
```rust
fn main() {
    // 1. a 拥有 Vec 的元素缓冲区。
    let mut a: Vec<i32> = vec![3, 7];

    // 2. 临时借用 a；最后一次使用后，不再继续这个借用。
    let r = &mut a;
    r[0] = 4;
    r.push(10);
    assert_eq!(r.as_slice(), &[4, 7, 10]);

    // 3. 显式克隆，b 拥有独立的元素缓冲区。
    let mut b = a.clone();
    b[0] = 99;
    assert_eq!(a[0], 4);

    // 4. 将所有权移给 c；此刻不能读取 a 的旧值。
    let c = a;
    assert_eq!(c, vec![4, 7, 10]);

    // 5. 重新初始化 a；这是一个新的 Vec 值。
    a = vec![1];
    assert_eq!(a, vec![1]);
    assert_eq!(c[0], 4);
    assert_eq!(b[0], 99);

    // 6. 正常离开作用域，c、b、重新初始化后的 a 各自 Drop。
}
```

这里没有在最后继续使用 `r`。如果在 `let c = a` 后面再通过 `r` 访问，借用就必须跨越移动，编译器会拒绝这个程序。借用检查使“还要使用旧借用，却把拥有者移走”无法作为安全 Rust 代码通过编译。

重新初始化 `a` 并不会使之前的借用自动成为对新值的合法借用。需要访问新值时，重新创建 `let r = &a;` 或 `let r = &mut a;`，由编译器检查新的借用区间。

### Python 完整程序

<!-- example: python-lifecycle -->
```python
def demo():
    # 1. a 绑定到一个列表对象。
    a = [3, 7]

    # 2. r 绑定到同一个对象，也能让对象继续可达。
    r = a
    r[0] = 4
    r.append(10)
    assert a == [4, 7, 10]

    # 3. 浅复制外层列表；这里的元素都是不可变整数。
    b = a.copy()
    b[0] = 99
    assert a[0] == 4

    # 4. c 与 a 共享对象；这里没有所有权 move。
    c = a
    assert c is a

    # 5. a 改绑到新列表；r 和 c 仍绑定旧列表。
    a = [1]
    assert a == [1]
    assert r is c
    assert r == [4, 7, 10]
    assert b[0] == 99

    # 6. 函数正常返回后，本例的列表没有其他持有者，可被回收。


demo()
```

Python 第 5 步与 C++ 的差异最值得逐行看：C++ 的 `r` 引用容器对象 `a`，给 `a` 赋值后它看到新内容；Python 的 `r` 独立绑定旧列表，`a` 改绑后它继续看到旧内容。

如果 Python 第 5 步改写成 `a[:] = [1]`，则是在原列表上修改内容，`r` 和 `c` 都会看到 `[1]`。**重新绑定名字与原地修改对象，是 Python 中观察别名行为时必须区分的操作。**

### 在第 5 步停下来，画出关系

```text
C++：
    r、p ──指向──> a：管理 [1]
                   c：管理 [4, 7, 10]
                   b：管理 [99, 7, 10]

Rust：
    旧 r 的借用已经结束，不能继续使用它跨越移动。
                   a：拥有 [1]
                   c：拥有 [4, 7, 10]
                   b：拥有 [99, 7, 10]

Python：
    a ──────────> 新列表 [1]
    r、c ───────> 旧列表 [4, 7, 10]
    b ──────────> 副本   [99, 7, 10]
```

三个程序都同时保留三组数据，但达到这个结果的过程不同。C++ 对原容器对象赋新值；Rust 先移动，再重新初始化原变量位置；Python 让名字绑定新对象，同时由其他名字保留旧对象。

## 8. 把变量传给函数或返回出去，规则如何继续？

函数调用沿用上面的规则，并不是额外的一套“所有变量都按引用传递”的机制。

| 意图 | Rust 参数 | C++17 参数 | Python 参数 |
|---|---|---|---|
| 读取原容器 | `a: &Vec<i32>`；更通用时用 `&[i32]` | `const vector<int>& a` | 形参名字绑定调用方传来的对象 |
| 修改原容器 | `a: &mut Vec<i32>` | `vector<int>& a` | 对形参所指列表调用修改方法或给元素赋值 |
| 接收一个拥有的容器值 | `a: Vec<i32>`，传入时移动或显式克隆 | `vector<int> a`，从左值通常复制，从 `move(x)` 可移动 | 不自动转移独占所有权，也不自动复制列表 |
| 返回函数中新建的容器 | 返回 `Vec<i32>`，所有权交给调用方 | 返回 `vector<int>` 值，可以进行返回值优化或移动 | 返回对象，调用方建立对它的绑定 |

Rust 和 C++ 的返回值也不要求“先把所有内容再复制一遍”。C++17 的局部命名返回值优化可能消除复制/移动；不进行该优化时，这里的可移动 `vector` 可以通过移动返回。Rust 从函数返回 `Vec` 是所有权转移。Python 返回列表时，调用方得到的是同一个列表对象，而不是对已经消失的局部名字槽位的引用。

Python 形参可以修改共享对象，但给形参重新赋值只会改绑形参。例如 `def f(x): x = [1]` 不会让调用方的名字 `a` 改绑；`def f(x): x.append(1)` 则修改了共同持有的列表。这通常称为对象共享或“传对象引用”，不能与 C++ 的可写引用参数完全等同。

对局部数据返回借用时，边界才不同：C++ 返回局部 `vector` 的 `T&` 或 `T*` 会让调用方得到悬空访问路径；安全 Rust 会拒绝返回指向已结束局部数据的引用；Python 返回列表对象后，外部绑定继续让对象可达。更详细的返回值例子见[函数返回值生命周期](ReturnValueLifetime.md)。

## 9. 最后退出作用域：谁消失，谁销毁，谁还能被访问？

回到第 7 节的程序，观察正常结束时的清理。这里讨论正常作用域退出，不把主动泄漏、强制终止进程等情况混入主线。

| 被追踪的东西 | Rust | C++17 | Python |
|---|---|---|---|
| `a` 这个名字 | 超出作用域不可再用；在作用域内也可能因已移动而不可读 | 超出作用域不可再用 | 局部名字随函数调用结束而释放绑定 |
| `a` 中的拥有者值 | 若仍已初始化，就执行 `Drop` 和成员清理 | 自动对象析构，成员随之清理 | 没有与此完全相同的独占拥有者值模型 |
| `r` 这样的借用/别名 | 借用结束，不负责释放目标 | 引用不负责销毁被引用对象 | 释放一个绑定可能减少对象的持有关系 |
| `p` 这样的裸指针 | 指针值结束不释放目标；目标失效后不得解引用 | 指针对象结束不执行 `delete` | 本文普通 Python 代码没有对应的裸指针 |
| 元素缓冲区 | 由拥有它的 `Vec` 清理 | 由拥有它的 `vector` 清理 | 由解释器管理列表及其持有的对象引用 |

Rust 的 `drop(a)` 消耗传入值，从而提前触发其清理；如果传进去的是共享引用 `&T`，结束的是引用值，不是被借用的 `T`。C++ 的智能指针 `reset()` 可以提前放弃拥有权；若是共享指针，要等最后一个强拥有者释放才清理目标。Python 的 `del a` 删除名字绑定，不等于“无论别人是否使用都强制销毁对象”。

容器“活着”也不表示它此前产生的所有元素引用一直有效。C++ `vector` 可能扩容而使元素迭代器悬空；Rust 阻止仍要使用元素借用时进行冲突修改；Python 获取 `x = a[0]` 是保留元素对象，随后 `a[0] = 9` 替换列表槽位，`x` 仍然指向原来的元素对象。容器寿命、元素寿命、访问路径的有效性，应当分别追踪。

对于文件、锁等需要及时释放的资源，C++/Rust 通常把释放动作放在资源拥有者的析构/`Drop` 中；Python 常用 `with` 确保退出块时执行约定的清理。对象内存何时回收与外部资源何时关闭，是两个相关但不能混同的问题。

## 10. 用你的提纲检查一行新代码

遇到 `a` 或 `b = a`，可以沿这条顺序推理：

1. **变量与初始化**：是在创建新对象/绑定，还是给已有目标赋值？初始化后有没有可读的值？
2. **类型**：`auto`/类型推导最终得到了 `T`、`T&`、`&T`、`Box<T>`，还是别的类型？Python 则分别看对象运行时类型和名字绑定。
3. **存储与寿命**：变量本身、目标对象、内部资源分别由谁持有？哪个退出事件负责清理？
4. **ref/ptr**：它指向整个容器、某个元素，还是持有资源的句柄？它是否负责保活？能否改指向？
5. **等号**：C++ 看构造/赋值重载和表达式类别；Rust 看 `Copy`、move、显式借用/clone；Python 看名字改绑还是对象属性/元素修改。
6. **后续使用**：原 `a` 能否继续使用？已有 `r`、`p` 现在访问什么？目标被移动、替换、扩容或销毁后，访问还是否合法？

这六步能够同时回答“值在哪里”“谁负责释放”“等号有没有复制”“引用为什么还能用”，而不必把某一种语言的变量模型直接套给另外两种。
